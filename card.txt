【拆卡直播间小程序——业务流程】

一、用户账户

1. 用户进入微信小程序。
2. 用户通过微信登录。
3. 系统创建或识别用户账户。
4. 用户账户可以关联：
   - 当前排队/服务状态
   - 购物车
   - 待结算订单
   - 历史订单

二、进入直播间

1. 用户进入拆卡直播间。
2. 查看当前直播状态。
3. 查看当前排队情况。
4. 用户可以选择加入排队。

三、加入排队

1. 用户点击“加入排队”。
2. 系统创建一次新的服务排队记录。
3. 系统分配排位号。
4. 服务状态变为 WAITING（等待中）。
5. 用户可以查看：
   - 当前排位号
   - 前面等待人数
   - 当前服务状态
   - 预计等待情况（如果系统提供）

四、等待期间

用户处于 WAITING 状态时：

1. 可以继续等待。
2. 可以浏览直播间商品。
3. 可以将商品加入购物车。
4. 可以修改购物车中的商品数量。
5. 可以查看购物车。
6. 暂时不能正式下单。
7. 用户可以主动退出排队。

五、退出排队

1. 用户点击“退出排队”。
2. 当前排队记录结束。
3. 排位状态变为 CANCELLED（已取消）。
4. 用户退出当前队列。
5. 用户购物车中的商品继续保留。
6. 用户以后可以重新加入排队。
7. 重新排队时创建新的排队记录，并获得新的排位号。

六、店员叫号

1. 店员在员工后台查看当前排队队列。
2. 店员选择下一位用户。
3. 系统将该用户状态变为 CALLED（已叫号）。
4. 用户收到叫号通知。
5. 用户响应叫号后：
   CALLED → ACTIVE（服务中）。
6. 用户没有响应时：
   店员可以选择“跳过”。
7. 被跳过的用户状态变为 SKIPPED（已过号）。
8. 过号后不能恢复原来的排位。
9. 用户需要重新加入排队。
10. 重新排队后获得新的排位号。
11. 原来的购物车商品继续保留。

七、服务开始

1. 用户响应叫号。
2. 排队状态变为 ACTIVE（服务中）。
3. 用户正式进入本次拆卡服务。
4. 用户可以：
   - 浏览商品
   - 加入购物车
   - 修改购物车
   - 删除购物车商品
   - 查看已经下单的订单
   - 继续下单

八、购物车

1. 购物车属于用户账户。
2. 购物车独立于排队状态。
3. 用户在 WAITING 状态可以加入购物车。
4. 用户在 ACTIVE 状态可以加入购物车。
5. 用户掉线后购物车继续保留。
6. 用户退出排队后购物车继续保留。
7. 用户过号后购物车继续保留。
8. 用户结束服务后购物车不会自动下单。
9. 员工强制结束服务后购物车也不会自动下单。
10. 只有用户主动点击“下单”，购物车中的商品才会生成正式订单。

九、主动下单

1. 用户在 ACTIVE 状态下进入购物车。
2. 用户确认需要购买的商品。
3. 用户点击“下单”。
4. 系统根据当前购物车商品创建正式订单。
5. 订单状态变为 UNPAID（待支付）。
6. 已经生成订单的商品从当前购物车中移除或标记为已下单。
7. 用户可以继续向购物车加入新的商品。
8. 用户可以再次下单。
9. 一次服务期间允许产生多个订单。
10. 下单不代表立即支付。
11. 用户可以之后再进行支付。

十、服务期间掉线

1. 用户在 ACTIVE 状态时掉线、退出小程序或网络中断。
2. 系统不自动结束服务。
3. 系统不自动下单。
4. 系统不自动清空购物车。
5. 系统不自动取消已经产生的订单。
6. 当前服务状态保持不变。
7. 用户重新进入小程序并登录后：
   - 恢复用户账户
   - 恢复当前服务状态
   - 恢复购物车
   - 恢复待支付订单
   - 恢复历史订单

十一、用户主动结束服务

1. 用户在 ACTIVE 状态下点击“结束服务”。
2. 系统确认用户是否确定结束服务。
3. 用户确认后：
   ACTIVE → FINISHED（服务结束）。
4. 本次排队/服务记录结束。
5. 购物车不会自动下单。
6. 购物车不会自动支付。
7. 购物车不会因为结束服务而自动清空。
8. 已经主动下单产生的订单继续保留。
9. 待支付订单继续保留在用户个人中心。
10. 用户以后可以在个人中心查看并支付待结算订单。

十二、员工强制结束服务

1. 员工可以在后台查看当前 ACTIVE 用户。
2. 员工可以选择“强制结束服务”。
3. 系统将当前服务状态变为 FINISHED。
4. 不自动将购物车商品生成订单。
5. 不自动支付。
6. 不删除购物车。
7. 已经产生的订单继续保留。
8. 待支付订单继续保留在用户个人中心。

十三、订单

1. 订单只在用户主动点击“下单”时生成。
2. 一个用户一次服务可以产生多个订单。
3. 订单生成后状态为 UNPAID（待支付）。
4. 订单与当前排队/服务状态相互独立。
5. 服务结束不会自动关闭订单。
6. 服务结束不会自动支付订单。
7. 用户可以在个人中心查看待支付订单。
8. 用户可以在个人中心主动进行支付。
9. 支付成功后：
   UNPAID → PAID（已支付）。
10. 已支付订单进入历史订单。

十四、个人中心

个人中心主要包含：

1. 用户信息
2. 当前服务
3. 当前购物车
4. 待结算订单
5. 历史订单

待结算订单：

- 查看订单详情
- 查看商品
- 查看订单金额
- 点击“立即支付”
- 完成微信支付

历史订单：

- 查看历史订单
- 查看订单详情
- 查看商品明细
- 查看订单金额
- 查看支付状态
- 查看订单时间

十五、排队状态

WAITING
等待中

WAITING → 用户退出 → CANCELLED

WAITING → 店员叫号 → CALLED

CALLED → 用户响应 → ACTIVE

CALLED → 用户无响应 → SKIPPED

SKIPPED → 用户重新排队 → 新的 WAITING

ACTIVE → 用户结束服务 → FINISHED

ACTIVE → 员工强制结束 → FINISHED

十六、核心业务原则

1. 排队决定用户当前的服务资格。
2. WAITING 状态可以加入购物车，但不能正式下单。
3. ACTIVE 状态可以正式下单。
4. 购物车属于用户账户，不属于某一个排位号。
5. 退出排队不会删除购物车。
6. 过号不会删除购物车。
7. 过号必须重新排队并获得新的排位号。
8. 掉线不会改变服务状态。
9. 掉线不会自动下单。
10. 结束服务不会自动下单。
11. 员工强制结束不会自动下单。
12. 只有用户主动点击“下单”才会产生订单。
13. 一次服务可以产生多个订单。
14. 下单和支付是两个独立动作。
15. 服务结束和订单支付也是两个独立动作。
16. 用户可以在服务结束后，通过个人中心处理待支付订单。
17. 支付完成的订单进入历史订单。


日本集换式卡牌卡包买取预约平台
产品逻辑与业务规则 V1.0
一、产品定位
这是一个面向日本集换式卡牌市场的「卡包买取信息聚合 + 预约撮合平台」。

平台连接两类用户：

商家：发布正在买取的卡包、买取价格、买取数量、买取时间段。

个人卖家：按照卡包或商家查找买取信息，预约出售卡包，并填写预计到达时间。

平台本身不参与线下资金结算，不提供线上支付。

核心流程：

卡包 → 商家发布买取信息 → 卖家预约 → 商家确认 → 数量锁定 → 卖家到店 → 实际交付 → 交易完成 → 双方互相评价。

二、用户类型
1. 普通卖家
个人用户，可以使用微信身份直接进入小程序。

不要求传统意义上的注册账号、用户名、密码。

首次使用时，可以通过微信身份自动生成平台内部 User ID。

卖家主要功能：

浏览卡包

搜索卡包

查看商家买取信息

查看预约状态

对商家进行评价

查看商家评价

2. 买取商家
商家需要拥有独立的商家身份，并经过平台审核。

商家主要功能：

发布买取信息

确认预约

评价卖家

查看自己的累计回收量

查看订单成交率

查看好评率

查看用户评价

3. 平台管理员
管理员负责：

V1.0 明确不做：

不做线上支付

不做线上发货

不做物流系统

「买取信息展示 + 预约 + 订单管理 + 信用记录 + 双方评价」。

十一、买取信息的修改规则
商家可以修改尚未结束的买取信息。

可以修改：

买取价格

公开买取数量

买取时间段

但是已经被商家确认的订单不会受到影响。

例如：

原买取价格：

¥185 /包

商家后来可以将公开买取价格修改为：

¥190 /包

之后新确认的订单按照 ¥190 计算。

已经确认的订单仍然保持原来的 ¥185。

十二、预约 Reservation
卖家看到买取信息以后，可以提交预约。

预约至少包含：

Reservation ID

卖家 ID

Buy Offer ID

预约数量

预计到达时间

创建时间

状态

卖家提交预约以后：

「不会立即锁定商家的数量」。

例如：

商家公开买取：

1,000 包

卖家 A 预约：

300 包

此时商家仍然可以显示：

剩余可预约数量：1,000 包

因为 A 的预约还没有被商家确认。

十三、商家确认预约
商家查看卖家的预约以后，可以：

确认

不处理

商家没有必须在多少小时内确认的时间限制。

但是：

如果买取时间段结束时，预约仍然没有被确认，则系统自动关闭预约。

自动关闭原因：

「店家未确认自动取消」

这种自动取消：

不影响卖家订单成交率

不影响商家订单成交率

十四、确认后的数量锁定
只有商家确认预约以后，数量才真正锁定。

例如：

商家买取：

1,000 包

卖家 A 预约：

300 包

商家确认：

300 包

此时：

公开买取数量：1,000
已锁定数量：300
剩余可预约数量：700

这 300 包正式进入已确认订单。

十七、确认后的数量锁定
确认后的订单数量不能直接修改。

例如：

300 包

商家不能直接改成：

200 包

确认后的订单时间段不能直接修改。

例如：

原订单：

10月1日 12:00～18:00

商家不能直接修改成：

10月1日 14:00～19:00。

如果无法按照原条件完成：

必须取消订单。

十九、确认后的订单不能修改，只能取消
已确认订单的以下内容全部锁定：

卡包

数量

价格

金额

买取时间段

已确认后如果出现变化：

只能取消订单。

不能直接修改订单。

二十、订单取消
双方都可以取消订单。

取消原因统一分为：

双方协商

店家未确认自动取消

店家原因

卖家原因

二十一、双方协商取消
如果卖家和商家协商一致取消：

取消原因：

「双方协商」

该订单：

不计为卖家失败

不计为商家失败

不影响双方订单成交率

二十二、店家未确认自动取消
如果卖家提交预约以后，商家一直没有确认。

买取时间段结束后：

系统自动关闭。

取消原因：

「店家未确认自动取消」

该订单：

不影响卖家订单成交率

不影响商家订单成交率

因为商家从未确认该交易。

二十三、店家原因取消
如果订单已经确认，之后商家主动取消：

取消原因：

「店家原因」

该订单：

不计为卖家失败

计入商家失败订单

影响商家订单成交率

二十四、卖家原因取消
如果订单已经确认，卖家主动取消：

取消原因：

「卖家原因」

该订单：

计入卖家失败订单

不计为商家失败

影响卖家订单成交率

二十五、卖家爽约
如果订单已经确认，卖家没有按照预约进行实际交付，例如没有到店或者没有按约交付：

商家可以将订单标记为取消。

取消原因：

「卖家原因」

该订单：

不产生完成交易

影响卖家订单成交率

不影响商家订单成交率

二十六、实际交付
卖家到店后，双方进行线下交易。

平台不处理付款。

商家确认实际收到数量。

例如：

预约数量：

300 包

实际收到：

298 包

商家输入：

298

系统记录：

实际交付数量：298 包

实际交易金额：

298 × 确认价格

例如确认价格为：

¥185 /包

最终金额：

¥55,130

二十七、交易完成
只有实际完成交付以后，订单才能变成：

「已完成」。

已完成订单需要记录：

实际交付数量

实际金额

完成时间

商家的累计回收数量增加：

实际交付数量

卖家的累计卖出数量增加：

实际交付数量

二十八、商家累计回收数量
商家对外展示：

「累计回收卡包数量」。

只统计：

已经完成交易的实际交付数量。

不能统计：

发布数量

预约数量

已确认但未完成数量

已取消数量

例如：

订单 A：实际完成 300 包
订单 B：实际完成 500 包
订单 C：取消
订单 D：实际完成 200 包

累计回收：

1,000 包。

二十九、卖家累计卖出数量
卖家对外展示：

「累计卖出卡包数量」。

同样只统计：

已经完成交易的实际交付数量。

例如：

300 + 500 + 200

累计卖出：

1,000 包。

三十、订单成交率
双方都拥有自己的订单成交率。

成交率只统计「已经进入确认阶段」的订单。

以下情况不进入成交率失败统计：

店家未确认自动取消

双方协商取消

三十一、卖家订单成交率
卖家成交率：

完成订单数 ÷ 有效确认订单数

其中：

以下情况计入卖家失败：

卖家原因取消

卖家爽约

以下情况不计入卖家失败：

双方协商

店家原因

店家未确认自动取消

例如：

确认订单 100 笔。

完成 95 笔。

卖家原因取消 3 笔。

双方协商 1 笔。

店家原因 1 笔。

那么：

卖家成交率：

95 ÷ (100 - 1 - 1)

= 96.94%

三十二、商家订单成交率
商家成交率：

完成订单数 ÷ 有效确认订单数

其中：

以下情况计入商家失败：

店家原因取消

以下情况不计入商家失败：

双方协商

卖家原因

店家未确认自动取消

例如：

确认订单 100 笔。

完成 95 笔。

店家原因取消 3 笔。

双方协商 1 笔。

卖家原因 1 笔。

那么：

商家成交率：

95 ÷ (100 - 1 - 1)

= 96.94%

四十、最核心的业务逻辑
整个产品必须遵守以下原则：

卖家可以不注册传统账号，通过微信身份直接使用。

商家必须拥有商家身份。

买取信息由商家发布。

买取信息包含卡包、价格、公开买取数量、买取时间段。

买取时间直接使用完整时间段，例如「10月1日 12:00～18:00」。

卖家可以按照卡包寻找商家。

卖家可以按照商家查看该商家正在买取的所有卡包。

卖家提交预约后，不立即锁定数量。

商家确认预约后，才锁定数量。

商家没有必须确认预约的时间限制。

买取时间段结束时，仍未确认的预约自动关闭。

自动关闭不影响任何一方成交率。

商家可以修改尚未锁定的买取信息。

买取信息的价格可以修改。

已确认订单的价格永久锁定。

已确认订单的数量永久锁定。

已确认订单的买取时间段永久锁定。

已确认订单不能修改，只能取消。

双方都可以取消已确认订单。

取消原因分为：双方协商、店家未确认自动取消、店家原因、卖家原因。

双方协商不影响任何一方成交率。

店家未确认自动取消不影响任何一方成交率。

店家原因取消影响商家成交率。

卖家原因取消影响卖家成交率。

卖家爽约按照卖家原因处理。

只有实际完成交易的数量才计入累计回收/累计卖出数量。

只有完成订单才能进行双方评价。

商家展示累计回收数量、订单成交率、好评率。

卖家展示累计卖出数量、订单成交率、好评率/评价。

平台不参与线下交易资金结算。

平台不提供线上支付。

平台主要负责信息展示、预约、订单记录和双方信用体系。

四十一、这份 V1.0 上继续往下拆，不要重新描述整个项目。产品最核心的用户路径
卖家：

按卡包找
→ 选择卡包
→ 查看多个商家的价格/数量/时间
→ 选择商家
→ 输入预约数量
→ 输入预计到达时间
→ 提交预约
→ 等待商家确认
→ 商家确认
→ 数量锁定
→ 到店
→ 实际交付
→ 订单完成
→ 评价商家

另一条路径：

按商家找
→ 选择商家
→ 查看该商家所有正在买取的卡包
→ 选择卡包
→ 预约
→ 后续流程相同

商家：

创建买取信息
→ 收到卖家预约
→ 查看卖家信用
→ 确认预约
→ 数量锁定
→ 等待卖家到店
→ 确认实际交付数量
→ 完成订单
→ 评价卖家

四十二、产品核心价值
对卖家：

「我手里的卡包现在去哪里卖、多少钱卖、还能卖多少、什么时候可以去。」

对商家：

「我发布今天想收什么卡包，并提前知道有哪些卖家准备带多少过来。」

平台的核心不是线上交易，而是：

「买取信息聚合 + 预约撮合 + 线下交易记录 + 双方信用体系。」

这份可以直接作为后续 AI 的项目总提示词/PRD 基础文档。如果下一次你要继续开发，我建议就在这份 V1.0 上继续往下拆，不要重新描述整个项目。
